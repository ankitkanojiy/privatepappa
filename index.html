Why Offline Encryption Apps Matter

Your phone may hold personal photos, videos, documents, recordings, and other sensitive files. A screen lock controls access to the device; file encryption adds a separate protection layer for selected vault content.

PrivateVault stores selected files in an encrypted app-private repository. Access requires the correct password-derived key or an enrolled biometric wrapper that Android authorizes.

The current Android manifests request neither INTERNET nor ACCESS_NETWORK_STATE. The apps do not include cloud sync, advertising, analytics, telemetry, or remote file-processing SDKs.

The protection boundary is still important: decrypted copies exported, shared, or opened in another app are no longer protected by vault encryption. Device compromise, storage failure, forgotten passwords, and unverified backups also remain user risks.

PrivateVault and PrivateVault PRO use the same local cryptographic foundation. PRO adds workflow, viewing, and authorization features without changing the core encryption used by the Free edition.

How PrivateVault & PrivateVault PRO Protect Your Data

Both editions use explicit encrypted formats, strict parsing, and authenticated state transitions rather than simple file hiding, renaming, or folder obfuscation.

Newly written and migrated vault files use the PVL2 format: chunked AES-256-GCM authenticated encryption with fresh nonces, ordered chunks, authenticated structural data, and strict length and trailing-data checks. Supported unmigrated PVLT1 files remain readable.

Current PVMD v2 metadata uses a separate AES-256-GCM envelope with a fresh nonce and authenticated structural header. It protects entries, folder relationships, revisions, and active encrypted-file references.

New vault credentials use PBKDF2-HMAC-SHA256 with exactly 600,000 iterations, a unique random 32-byte salt, and a 256-bit derived key. The current implementation does not use Argon2id.

New encrypted backups use PVBAK4 and a fixed PBKDF2-HMAC-SHA256 profile with 600,000 iterations, a fresh random 32-byte salt, and a 256-bit derived key. Supported PVBAK1, PVBAK2, and PVBAK3 backups retain their historical restore behavior.

Password-first biometric enrollment uses Android BiometricPrompt and an authentication-bound Android Keystore key. PrivateVault does not receive or store biometric templates and does not claim that every active key is StrongBox- or hardware-backed.

  • ✦ PVL2 chunked AES-256-GCM vault files
  • ✦ PVMD v2 authenticated metadata
  • ✦ Versioned password-verifier precheck
  • ✦ PBKDF2-HMAC-SHA256 password derivation
  • ✦ PVBAK4 encrypted backups
  • ✦ Transactional restore and migration flows

Technical Accuracy Note

Legacy formats are retained for compatibility. Current formats improve authenticated structure, but no software can guarantee recovery from pre-existing corruption, storage failure, device compromise, or a forgotten password.

📥 Upgrading from PrivateVault to PrivateVault PRO 👑

To move vault data to PrivateVault PRO, create a password-protected encrypted backup in PrivateVault and save it to a location you control. In PrivateVault PRO, choose Restore, select the backup, and enter the same backup password. The Android apps perform this workflow locally without cloud transfer. Keep the original backup until you verify the restored vault.

Limitations

PrivateVault and PrivateVault PRO do not guarantee that every file type will preview or render perfectly. Unsupported, malformed, very large, unusual, or resource-intensive files may fail or behave differently depending on the device. Scan-to-PDF quality depends on image quality, lighting, document angle, and device capability.

Authenticated encryption detects modification and many forms of truncation; it does not repair missing data. PrivateVault uses staged and transactional workflows, but device failure, exhausted storage, filesystem errors, or process interruption can still prevent an operation from completing.

Do not manually move, rename, or modify PrivateVault's app-private files. Keep sufficient free storage, use the built-in import, export, backup, and restore tools, and maintain independently verified backups before major operations.

The developer has no server-side password reset or recovery key. If a vault or backup password is lost, encrypted data may become permanently inaccessible. Exported or externally opened decrypted copies are outside PrivateVault encryption, and deletion cannot guarantee physical secure erasure on flash storage.
